# Walking route planning

Version 0.36.6 / build 261 uses compact Atlas controls on the existing main map. Plan a walk hides the normal panels and navigation dock. Create and Suggest are the only choices; there is no Saved option. Descriptive Create/Suggest choices, a gold validation action and a blue-accent guidance card clarify the existing flow. French/English, appearance modes, safe areas and reduced-motion map framing remain supported.

## Using the planner

Choose Plan a walk, then Create or Suggest. Both first ask you to tap a starting point anywhere on the map, independently of GPS permission or your present location. Pan to another area before choosing. Close/back restores the normal map controls and any previously validated guidance.

Create accepts a start and up to nine further points. Tap each next point directly on the map; the route recalculates automatically from the second point onward. Numbered markers identify selections. Undo removes the last point, allowing replacement. Return is enabled initially; disable it for an open walk. Manual edits preserve the viewport. Validate walk becomes available once a valid route has been calculated.

Suggest calculates automatically after the first start tap, initially targeting 2 km. Choose 2, 4 or 6 km, toggle Return, refresh for another candidate, or tap a different starting point; each change recalculates automatically. Suggestions prioritize unique valid unexplored cells. The computed route is framed on the main map. Estimated times use 4.5 km/h, excluding breaks. Actual routes may range from 75% to 115% of the target, with an absolute 6 km maximum, also applied to manual plans. The summary displays actual distance, estimated time and approximate new-cell count before validation. Fully explored areas can return zero new cells; suggestions are bounded heuristics, not globally optimal tours. Refresh may produce the same best route where alternatives are limited.

Validate walk persists blue guidance, closes preparation and restores ordinary controls without starting GPS recording. Travel to the selected start separately and tap Start walk when ready. The app does not enforce proximity to the starting point. Blue route geometry differs from gold live recording and teal inferred links. Guidance shows straight-line start distance before recording and an off-route message above 50 m from the nearest route segment during recording. Segment distance uses a prepared local projection for routes up to 6 km; sparse OSM vertices no longer cause false warnings along a straight segment. Missing location shows a waiting state. It does not provide automatic rerouting or turn-by-turn/voice directions. Tap guidance to frame the plan; Hide removes it without changing recording. Planning never awards territory, completion or medals.

Planning markers use provider-aware snapshots: Apple MapKit uses native annotation views without redraw; Google/Android refresh after layout and stop tracking once the snapshot settles. Pending redraw timers cancel on provider change or unmount. This fixes the native command error reported in 0.36.1.

## Routing and limits

Planning uses public Overpass endpoints and on-device graph search, without accounts, keys, billing, new native dependencies or a backend. Uncached areas require internet. Downloaded topology is cached for seven days, retaining three bounded areas. The maximum requested radius is 6.5 km; dense areas can exceed 90,000 elements, 70,000 vertices or a 12-million-character response and fail clearly. Requests have 28-second deadlines including body consumption and sequential failover; incomplete responses are rejected. Response size is checked after text consumption when Content-Length is missing, so this is not a streaming memory bound.

Input changes debounce for 350 ms, abort previous requests and invalidate their previews. Cancellation, closing and backgrounding discard unfinished work. Late responses cannot replace current inputs or reappear after closing. Validation handles persistence errors without losing the preview.

The planner is separate from historical GPS-gap inference. Exact OSM node identity supplies junctions; coordinate crossings do not connect roads or bridge levels. Accepted edges are subdivided to at most 10 m for snapping and sampling. Stops snap within 40 m; the blue path follows snapped locations, while numbered preparation markers retain the tapped positions. No connector across unverified ground is drawn. Pedestrian overrides, pedestrian one-way tags, steps, node barriers, conditional access and opening times are handled conservatively. Unknown barriers, unresolved restrictions, indoor ways and area polygons are excluded. Forbidden Zone cells remove crossing edges. Missing paths, unmodeled relations, errors and closures can still affect results; observed signs and access conditions take precedence.

Bounded, yielding A* searches join manual stops. Suggested tours sample angular sectors, penalize repeated edges and rank eligible candidates by distance and unique unexplored cells. One smaller candidate ring is tried if the first cannot fit. Discovery uses the canonical 15 m Mercator exploration grid and the same segment sampling/capture radius as recorded paths, not arbitrary point samples or straight-line area. Each cell counts once, including on return routes. Stored exploration, already-filled small enclosures and Forbidden Zones are excluded. Cell eligibility is cached per exploration snapshot. This remains a path-capture estimate: it does not predict additional future loop-fill rewards, GPS quality or guaranteed completion. Existing non-discovery routing preferences remain internal for compatibility but are not shown in the simplified UI.

OSM data is attributed in the planner. References: [access tags](https://wiki.openstreetmap.org/wiki/Key:access), [Overpass public instances](https://wiki.openstreetmap.org/wiki/Overpass_API), [OSM copyright and ODbL](https://www.openstreetmap.org/copyright).

## Persistence and backup

The following_route_plan setting stores an immutable guidance snapshot when Validate walk succeeds. Recording creation binds it to the session ID in the same exclusive transaction. Launch recovery loads guidance only for the matching active/recoverable session or a pending plan with no recording. Finalized/discarded sessions cannot attach old guidance to a new walk. Retained geometry works offline; native basemap tiles are not guaranteed offline. Unvalidated preparation is temporary and resets on closing/backgrounding.

Migration 38 retains route_plans and planning_cache. The Saved tab, naming form and library controls have been removed, but legacy plan records are not deleted. Validation no longer creates a library entry. The repository's existing 50-plan limit and backup support remain for compatibility. Optional estimatedNewCellCount allows older plans without this field to remain valid; this patch requires no new migration.

Backup V5 preserves optional legacy routePlans metadata and restores it transactionally. Older V5 archives without routePlans remain accepted and restore an empty legacy library. Disposable topology and guidance snapshots are not exported; restore clears both. Older app versions may drop optional metadata when re-exporting; keep the original archive when transferring versions.

## Validation

npm run test:planning exercises pedestrian topology, restrictions, Forbidden Zone detours, one-way walking, canonical grid/capture equivalence, unique cell counts, filled-surface exclusion, cancellation and 2/4/6 km suggestions. A component callback/effect harness tests remote starts, successive taps, undo, automatic suggestions, validation and stale-result rejection. It does not render native UI. SQLite tests cover legacy CRUD/limits, atomic recording association, reward isolation, V5 roundtrip, offline/network failures and guidance recovery/write failures. Resilience tests cover transactional restore and older archives. All run in npm test.

Native rendering, touch targets, accessibility, real pedestrian networks and performance require the physical-device protocol in [Testing](TESTING.md#walking-route-planning---0362). The development environment could not resolve public Overpass hosts during the previous live smoke check. Injected network fixtures do not establish successful real-server routing or physical-device performance.
